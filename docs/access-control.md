# Вход и права сотрудник / HR

Роль и связь с сотрудником хранятся в SQLite, отдельно от карьерного профиля.
Названия должностей из датасета (например, HR Business Partner) не дают права HR.
Клиент не может назначить роль через JSON, query-параметр или заголовок.

## Матрица доступа

| Запрос | Без сессии | Сотрудник | HR |
| --- | --- | --- | --- |
| `/health`, `/docs`, `/openapi.json`, login | Открыто | Открыто | Открыто |
| `/auth/me`, logout | 401 | Своя сессия | Своя сессия |
| `/events`, `/skills` | 401 | Разрешено | Разрешено |
| `GET /employees` | 401 | 403 | Разрешено |
| Профиль, история, рекомендации, траектория, выполнения | 401 | Только свой ID | Любой ID |
| Симуляция | 401 | Только свой ID | Любой ID |
| Создать выполнение | 401 | Только свой ID | Только свой ID при наличии привязки |
| `/hr/summary` | 401 | 403 | Разрешено |

Пути указаны без префикса `/api/v1`, кроме `/health`, `/docs`, `/openapi.json`.
Проверка чужого ID возвращает 403 до чтения БД/вызова движка: это не раскрывает,
существует ли такой профиль. HR получает 404 для отсутствующего профиля.
HR-обзор пока содержит только количество сотрудников, записей истории,
завершённых записей истории и новых выполнений приложения. Дефициты и UI — позже.

## Учётные записи

Самостоятельной регистрации нет. Администратор с доступом к компьютеру запускает:

```bash
.venv/bin/python -m backend.app.manage_users create employee1 --role employee --employee-id E0001
.venv/bin/python -m backend.app.manage_users create employee2 --role employee --employee-id E0002
.venv/bin/python -m backend.app.manage_users create hr --role hr
```

Пароль запрашивается скрытым вводом и не передаётся аргументом командной строки.
Минимум 12 символов, максимум 256. Логин: 2–64 латинские буквы, цифры, `.`, `-`, `_`;
регистр логина не учитывается. Один профиль связан максимум с одной учётной записью.
HR может иметь свой `--employee-id`, но он не обязателен. Новому сотруднику
нужно сначала импортировать профиль, затем создать учётную запись.

```bash
.venv/bin/python -m backend.app.manage_users set-password employee1
.venv/bin/python -m backend.app.manage_users disable employee1
```

Смена пароля и отключение отзывают все сессии пользователя. Параметры БД берутся
из `CQ_DB_PATH`, как у API. Учётные записи не создаются автоматически при запуске;
в репозитории нет паролей или готовых пользовательских сессий.

## HTTP-вход

`POST /api/v1/auth/login` принимает JSON `{username, password}` и возвращает:
`access_token`, `token_type: bearer`, `expires_at`, `user` (ID, логин, роль, профиль).
В Swagger выполните login и вставьте **только значение access_token** в Authorize.
Обычный клиент отправляет `Authorization: Bearer <access_token>`.
`GET /auth/me` восстанавливает сведения о текущем пользователе.
`POST /auth/logout` отзывает текущий токен и возвращает 204.

Frontend должен держать токен в памяти, не добавлять его к URL и удалять при выходе
или 401. Авторизационных cookies нет: браузер не прикладывает токен автоматически.
Для CORS разрешён заголовок Authorization. Для работы вне localhost нужен HTTPS.
Пароли и токены нельзя включать в логи/репозиторий; API отвечает `Cache-Control: no-store`.

## Хранение и проверки

- Пароли: PBKDF2-HMAC-SHA256, 600 000 итераций, отдельная случайная соль 16 байт.
  Параметры соответствуют [рекомендациям OWASP для PBKDF2](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Сессия: случайный токен 32 байта; в БД хранится только его SHA-256 и срок действия.
  По умолчанию срок — 8 часов, `CQ_SESSION_TTL_SECONDS` допускает 60–86400 секунд.
  Используется реальное время, не `CQ_AS_OF_DATE`.
- Каждый запрос заново проверяет сессию, активность учётной записи и роль в БД.
- 10 попыток входа на нормализованный логин за 5 минут. Лимит хранится в SQLite,
  сохраняется при перезапуске, успешный вход сбрасывает счётчик. Ошибки неизвестного
  пользователя, неверного пароля и отключённой записи одинаковы.
- SQLite автоматически обновляется с версии 1 до 2 добавлением таблиц accounts,
  sessions и login_attempts. Профили, история и выполненные задачи сохраняются.

Веб-кабинет на порту 5173 уже поддерживает вход, выход и сброс состояния при 401.
Токен хранится в памяти; перезагрузка страницы требует нового входа.
HR без привязки к профилю видит объяснение, а не данные другого сотрудника.

Ограничения этапа: нет SSO, восстановления пароля по почте, MFA или интерфейса
управления учётными записями. Локальный CLI выполняет административные действия.
