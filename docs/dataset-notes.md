# Результаты изучения стартового датасета

Данные синтетические. Дата среза: **2026-10-01**. История: **2024-10-01 — 2026-09-30**.

## Состав

| Файл | Содержимое |
| --- | --- |
| employees.json | 200 сотрудников; 8 ролей; Junior, Middle, Senior, Lead |
| skills.json | 60 навыков, шкала 0–5, 32 профиля требований, критические навыки |
| events.json | 40 мероприятий: 4 обязательных и 36 добровольных |
| activity_history.csv | 2 743 записи участия |

У 66 сотрудников нет карьерной цели. У 28 цель предполагает смену роли. Эти случаи должны обрабатываться явно.

## Правила обработки

- Отсутствующий навык означает уровень 0.
- Навыки профиля отражают последнюю оценку. Более раннюю историю нельзя повторно прибавлять к ним.
- Прирост завершённой активности определяется `gain` и `max_level`. Если текущий навык уже выше `max_level`, он не уменьшается.
- Обязательные мероприятия исключаются из рекомендаций развития.
- При отборе учитываются роль, грейд, предварительные требования, расписание и история.
- Завершённое добровольное мероприятие повторно не предлагается; исключение — клуб `EV_036`.
- Процент соответствия требованиям не отменяет критические дефициты.

## Обнаруженные особенности

1. В истории есть 544 последующие записи по уже завершённым обязательным мероприятиям `EV_001–003`. README формально запрещает повторы, но описания этих мероприятий указывают ежегодное обучение. Их нельзя просто удалить как дубликаты.
2. Для `self_paced` поле `date` — дата зачисления или назначения, а не завершения. Точной даты завершения нет; текущий адаптер использует date как приближённую дату завершения и сообщает об этом в UI. При наличии completed_at приоритет у неё.
3. Ни одно мероприятие не развивает `SK_TEST_DESIGN`. Не все дефициты можно закрыть существующим каталогом.
4. Для добровольных мероприятий отсутствует `due_date`: объяснение не должно утверждать своевременное выполнение без подтверждающих данных.
5. README доступен на трёх языках; названия и описания в исследованных JSON — на английском.

## Выполненная проверка данных

Проверены уникальность идентификаторов, ссылки между файлами, существование руководителей и их роли, диапазоны навыков и оценок, стаж, сортировка истории и неубывание требований по грейдам. В этих проверках ошибок не обнаружено. Особенность повторов обязательного обучения описана выше.

## Пример для проверки алгоритма

Сотрудник `E0001` — Junior Backend Engineer с целью Middle. API Design равен 2 при требовании 3 и является критическим навыком. Активность `EV_005` — System Design Fundamentals — подходит по текущей роли и грейду и повышает API Design и System Design. Это проверяемый кандидат, но не обещание закрыть все требования к повышению.
